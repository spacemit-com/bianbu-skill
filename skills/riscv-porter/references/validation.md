# 数据路径与兼容层验证

当迁移涉及编解码、解析器、SIMD/intrinsic 兼容层、未对齐内存或密集位运算时使用本指南。普通业务代码无需机械套用全部项目。

## 先验证契约

- 从公开头文件、README 和调用方整理入口、输入前置条件、返回值和错误行为。
- 将每个公开入口映射到上游测试。缺口用小型确定性测试或独立参考实现补齐。
- 随机测试的数据必须满足 API 前置条件。例如只对有序序列定义的 search/select，不得用无序随机输入宣称验证成功。
- 覆盖长度和对齐边界：`0/1`、向量宽度前后、块大小前后、尾部不足一块、所有可能的输入地址偏移，以及格式允许的最小/最大值。

## 兼容层验证

- 建立“项目实际使用的 intrinsic/API → 实现 → 覆盖它的测试”清单。
- 检查符号/无符号扩展、饱和与回绕、lane 顺序、shuffle 高位清零、立即数范围、未对齐 load/store、别名和端序。
- 大型兼容层优先进行 intrinsic 级差分；端到端测试通过不能证明每个仿真语义均正确。
- 使用扩展语法或编译器属性时，准确写明 GNU/编译器扩展；除非相应严格标准模式实际通过，否则不要宣称“纯 C99/C++11”。

## 动态与编译器检查

在工具链可用且成本合理时，以独立构建目录运行：

```sh
cmake -S . -B build-sanitize \
  -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_C_FLAGS='-O1 -g -fsanitize=address,undefined -fno-omit-frame-pointer'
cmake --build build-sanitize -j2
ctest --test-dir build-sanitize --output-on-failure
```

按项目语言调整选项。对严格别名、转换和移位可额外启用 `-fstrict-aliasing -Wstrict-aliasing=2 -Wconversion`，但区分新告警与无关存量告警。

Sanitizer 输出正确但有 runtime error 仍算失败证据。定位到上游既有代码时，用 revision/blame 证明来源，并判断当前迁移是否使该路径可达；不要因不是本次新增行而删除证据。

## 非法指令与优化器生成代码

- 保存退出码、信号类型、故障地址、对应函数/源码行及最终产物的反汇编。
- 使用同一源码构造最小变量对照，例如默认优化、关闭自动向量化、降低 ISA 基线；每次只改变一个因素。
- 独立指令探针用于排除候选，不足以证明整段自动生成序列或硬件实现正确。
- 优先把规避参数放到故障翻译单元；同时复测库内未故障但可能受全局参数影响的编码、哈希或其他热点。
- CMake/Make 等所有交付构建路径使用等价粒度。对每种编译器使用其支持的参数；“编译器接受参数”不等于运行时验证通过。

## 证据质量

- 记录命令、退出码、日志位置和触发输入。
- 独立参考实现不得复制被测算法的关键表达式。
- benchmark 与正确性测试分开；绝对吞吐不能替代同条件基线。
- 新增 SIMD/RVV 的差分测试必须作为证据保留，不得只在会话中输出一次结果后删除源码。记录固定随机种子、输入分布、长度/对齐边界、参考实现来源和编译参数。
- 性能对比前检查符号地址、分发日志或反汇编，确认不同算法标签没有通过弱别名或包装器落到同一实现；同一 fallback 的多个名称只能算一次实现。
- 报告完成后抽查原始日志、文件权限和统计命令；不要让中途状态或未跟踪文件造成最终声明失真。
