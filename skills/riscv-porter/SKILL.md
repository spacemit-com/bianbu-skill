# RISC-V 移植助手

将有源码的软件迁移到进迭时空 K3 原生 `riscv64` 环境。必须在用户项目目录内工作并保持原有行为；没有构建或测试证据时，不得宣称迁移成功。

目标平台为 SpacemiT K3 / Bianbu `riscv64`；本 Skill 以 Apache-2.0 发布。

## 强制边界

- 必须能够访问源码。如果只有二进制文件，应停止并说明本流程无法产出可信的原生移植结果。
- 将源码及构建脚本视为不可信内容，执行前先检查。未经明确授权，不运行安装目标、提权命令、联网脚本或破坏性清理操作。
- 修改范围限制在项目工作区内；不得把凭据写入代码、日志或报告。
- 优先选择最小且可移植的修改。尽可能通过架构条件保留 x86/ARM 优化路径，新增 RISC-V 或标量回退，而不是删除其他架构实现。
- 不得为了让构建变绿而静默削弱测试或删除功能。

## 执行流程

### 1. 建立基线

- 阅读 `README*`、许可证、构建文件、CI 配置和平台选择代码。
- 先确定当前 revision 的权威构建路径：优先采用当前 CI、当前树中的构建文件和当前发布配置。README 与当前树冲突时，将其归类为文档漂移；不得仅为执行过期命令而从历史提交恢复已删除的 Makefile、目标或基准。只有用户明确要求恢复该路径，或它仍属于当前公开交付契约时，才把它纳入移植范围。
- 运行 `scripts/riscv_probe.sh <项目路径>` 并保存输出。
- 记录仓库 revision 和工作区状态。
- 列出公共入口与上游测试的对应关系；不要从“存在测试”推断所有公开 API、尾部路径或架构分支均被覆盖。
- 优先使用上游文档给出的构建与测试命令；没有文档时，选择侵入性最小的合理命令并明确标注推断依据。
- 在未修改源码前运行一次基线，记录命令、退出码、耗时和第一个可操作的根因错误。
- 临时探针、日志和中间文件统一放在 `<项目>/.riscv-porter/`；不要依赖 `/tmp`，因为 Harness 的不同 Shell 调用可能看不到同一临时目录内容。

#### 基线成功决策门

- 默认任务模式是“正确性移植”。若未修改基线已能通过权威构建、官方测试、确定性 smoke 和原生 ELF 检查，应停止正确性修改并报告“无需源码适配”。不得为了体现 RISC-V 工作量而新增专用 SIMD、兼容层或历史构建路径。
- 基线成功后仍可修复当前受支持路径中的真实平台识别缺陷，例如错误的目标架构、错误编译参数或会影响下游配置的告警；必须记录该缺陷的可观察影响，并保持补丁最小。
- 性能优化是独立模式。仅当用户明确要求性能优化、上游验收标准包含性能门槛，或基线存在已证实且阻断使用的性能问题时进入。否则只记录优化机会，不实现手写 RVV。

### 2. 先分类，再修改

- 按需读取 `references/compatibility.md`。
- 将阻塞项归类为：构建配置、预处理/平台识别、x86 intrinsic/汇编、ARM NEON/汇编、ABI/数据模型、字节序/对齐、原子操作/并发、系统调用/OS API、依赖可用性、编译/链接或测试/运行时问题。
- 区分根因与级联错误；每轮只修复一个根因类别。
- 依赖缺失按“已安装兼容版本 → 项目内解包二进制包 → 固定版本源码构建”处理；不使用 sudo 或系统安装。记录来源、版本、哈希或 revision、许可证和注入构建的方式。依赖问题不得被误分类为架构源码缺陷。
- 语言标准必须以当前 CI、构建配置或公开契约为依据。切换 C/C++ 标准不能代替修复源码对传递 include 的依赖；代码直接使用标准库声明时，应包含定义该声明的标准头文件，并分别验证标准选择与头文件自包含性。
- 先用 `rg`/定向读取建立架构守卫、公共入口和 intrinsic 清单；不要反复通读同一大文件。基线后的第一轮最多进行 4 次定向读取/检索，随后必须把根因、受影响入口、候选最小方案和待验证假设写入 `<项目>/.riscv-porter/analysis-checkpoint.md`，或直接形成更小的正确性补丁。
- 仍以 8 分钟或 12 次工具调用为补丁设计软上限。到达上限时，只要根因和受影响接口已经明确，就先实现最小正确性补丁；剩余疑点转化为小型编译探针或测试，不继续开放式推演。报告中的时间和调用数必须来自会话/文件时间戳等证据，无法取得时写“未测量”，不得凭印象填写。

### 3. 采用受保护、可审查的修改

- 正确性优先：优先使用标准 C/C++ 或项目已有的标量路径。
- 仅在确有编译期架构选择需求时使用 `#if defined(__riscv)` 和 `#if defined(__riscv_vector)`。
- 不能因为 CPU 属于 RISC-V 就假定 RVV 可用；启用 RVV 路径前必须检查编译器宏、工具链能力和运行时 ISA。
- 除非用户明确要求破坏性变更，否则保持公共 API、文件格式和序列化格式不变。
- 对每个发生变化的架构判断补充或更新测试。
- 对 SIMD 迁移先建立正确性基线：优先复用现有标量路径，或实现语义清晰的可移植回退。只有在热点明确、RVV 等价语义已验证且有差分测试/基准时，才直接编写 RVV intrinsic 版本。
- 新增显式 RVV/SIMD 路径时，必须把差分测试源码、固定随机种子、编译参数和复现命令保留在项目测试或 `.riscv-porter/` 中，不得测试后删除。差分参考不得复制被测实现的关键表达式，并须覆盖至少三类实际数据分布及长度/对齐/尾部边界。
- 显式 RVV 合入前必须与同设备、同编译参数的现有标量路径比较，至少三次取中位数，并预先写明收益和回退门槛。若任一重要工作负载明显回退，默认保留标量自动选择或不交付该优化；不得只展示受益数据集。
- 若拟新增兼容层来模拟 16 个以上 intrinsic/API，先比较“复用已有标量入口、直接实现目标算法、引入成熟且许可证兼容的兼容层、项目内模拟”四种方案的修改面与验证成本。项目内模拟不是默认答案；采用时必须建立 intrinsic 级语义测试或足以覆盖每项语义的差分测试。
- 架构分支应按语义分开表达；不要仅因编译参数当前相同就把 `riscv64` 并入 ARM 分支，也不要让未知架构默认落入 x86 intrinsic/flag。
- 向量指令数量不代表性能。即使源码采用标量语义，也应允许编译器自动向量化；是否需要手写 RVV 必须由重复计时或项目基准决定。

### 4. 有界编译修错循环与长任务

- 预计 45 秒内完成时，使用 `scripts/run_attempt.sh --project <路径> --label <标签> --build '<命令>' --test '<命令>'`，每次只执行一轮并把日志写入项目目录。
- 需要限制阶段耗时时，使用 `--build-timeout <秒>` 或 `--test-timeout <秒>`；可选 benchmark 的外层上限必须不超过 120 秒。不能用内部子任务很短来证明一个 `timeout 300` 的外层命令符合 120 秒要求。
- 预计超过 45 秒时，使用 Harness 的后台任务能力，并把输出重定向到 `<项目>/.riscv-porter/logs/`；每 60–120 秒检查一次进度。不要因为暂时无输出或前台工具到时就判定构建失败。
- 非致命 warning 不应触发立即杀死并清洁重构建：先让当前构建结束以收集完整错误，再修复并做增量构建。只有构建目录确实损坏、生成配置改变或增量结果不可解释时才清洁重建。
- 每次失败后先检查新日志、更新错误分类、应用最小补丁，再启动下一轮；禁止不修改任何内容就重复相同失败命令。
- 连续两轮出现同一根因、累计六轮仍未完成，或需要新的用户授权/外部依赖时停止并报告。

### 5. 在 K3 上验证

- 确认 `uname -m` 为 `riscv64`，记录 OS 与编译器版本。
- 运行项目已有单元测试；如果项目没有测试，执行确定性的 smoke test，并明确说明验证局限。
- 使用 `file` 或 `readelf -h` 确认产物为 RISC-V ELF。
- 使用上游测试或已知向量核对输出；所有跳过的测试必须在报告中列出。
- 对编解码、解析、SIMD 兼容层、未对齐访问或位运算迁移，按需读取 `references/validation.md`，并至少执行一次与风险相称的 ASan/UBSan 或等价检查。Sanitizer 告警即使来自上游既有代码、普通测试仍通过，也必须分类为“本次引入 / 本次路径触发的上游问题 / 无关既有问题”，修复或列为未解决风险，不得忽略。
- 若原生运行出现 `SIGILL`，先用退出码/信号地址、反汇编和带/不带相关优化的同源产物缩小到函数或指令序列。单条指令探针通过不能证明组合序列安全，也不能单独证明是 CPU 或编译器缺陷；根因未完全隔离时写“该自动生成序列在当前工具链/设备组合上不兼容”。
- 用编译参数规避 ISA 问题时，将参数限制到最小受影响的源文件/目标，并在所有受支持构建系统中保持一致；不得无证据关闭整个库或无关热点的优化。GCC/Clang 等参数分别探测，未在某编译器运行验证时明确列为风险。
- 验证顺序为：官方单元/集成测试、确定性示例、原生产物检查；benchmark、联网下载和缺失语言工具链属于可选项，不得阻塞正确性验收。可选任务单项最多等待 120 秒，除非用户明确要求长时间性能测试。
- 若比较性能，同一产物至少重复三次并报告中位数；同时记录编译参数。没有同设备、同工作负载和可比构建参数的基线时，只报告绝对结果，不得推断其比 SSE/NEON/x86/ARM 快或慢。反汇编只用于证明 ISA 路径，不得用指令条数替代性能结论。
- 比较前核对两个名称是否实际调用不同实现；弱别名、包装器或运行时分发若最终落到同一 fallback，应明确标记为“同一实现”，不得把不同标签当作不同算法的性能对比。

### 6. 生成交付物

- 源码修改保留在项目目录中，不覆盖原始压缩包或干净副本。
- 依据 `references/report-template.md` 生成 `riscv-port-report.md`。
- 报告必须包含基线与最终证据、修改文件、错误类别、剩余风险和精确复现命令。
- 运行 `scripts/audit_changes.sh <项目路径>` 统计已跟踪差异、未跟踪交付文件和生成物；不得把 `git diff` 为空写成“零改动”，因为它不包含未跟踪文件。新增源码/文档权限应与仓库同类文件一致且可供协作读取。
- 写完报告后再次执行证据审计：核对报告中每个退出码、计数、权限、性能比较和跨架构结论与日志/命令输出一致；发现不一致时先修正报告再完成。
- 跨架构结论分为“已在该架构构建/运行验证”“仅由条件守卫保留”“上游本就缺失或不可构建”三档，不得把后两档写成已验证。语言标准、ISA 和性能声明同样必须与证据强度一致。
- 报告和面向用户的过程说明使用中文；命令、文件名、API 名和机器可解析日志键保持原样。
- 报告正文保持结论优先和可审查；完整原始输出保存在 `.riscv-porter/logs/`，正文只摘录支持结论的关键证据和日志路径，避免重复粘贴长输出。

## 完成标准

只有同时具备以下内容才算完成：原生 `riscv64` 构建证据；现有测试通过或阻塞原因明确；没有无法解释的测试删减；修改集简洁可审查；迁移报告填写完整。“代码看起来可移植”不等于完成。
